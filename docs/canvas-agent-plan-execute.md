# 画布 Agent：Plan & Execute

## 执行边界

`ChatService → claim/积分预留 → ContextBuilder → Planner → 校验并保存计划 → Executor → Verifier → 消息与积分事务提交 → release`

Planner 只输出 JSON，不持有画布写工具，也不负责执行循环。Executor 使用已校验、已落库的计划执行 MCP 工具；它负责版本、步骤结果引用、重试与检查点。Verifier 比较计划预期与真实画布；最终操作回复由程序依据已核验结果生成。普通问答和澄清使用无执行步骤的计划。

当前使用显式的持久化状态机，替换原来模型自行决定下一次工具调用的 LangGraph 循环。数据库中的计划和操作凭证是恢复依据，不依赖进程内聊天消息或框架内存。

## 文件职责

- `canvas-agent.service.ts`：阶段编排、规划校验、执行、核验、取消、超时。
- `agent-plan.ts`：计划 Zod schema、从工具定义派生 Planner JSON schema、步骤依赖引用、用户明确名称与创建数量约束。
- `agent-context.ts`：上下文筛选、历史窗口、输入预算。
- `agent-store.ts`：请求幂等、画布租约、过期接管与写入栅栏、错误分类。
- `agent-verifier.ts`：并发编辑前置条件和执行结果验证。
- `canvas-tools.service.ts`：业务验证、权限、画布 CAS、画布修改与步骤凭证原子提交。

## 计划

```json
{
  "mode": "execute",
  "goal": "重命名目标节点",
  "answer": "",
  "steps": [
    {
      "id": "rename",
      "description": "将节点名称改为测试agent",
      "tool": "rename_node",
      "arguments": { "nodeId": "真实节点ID", "title": "测试agent" }
    }
  ]
}
```

`mode` 为 `execute | answer | clarify`。执行计划最多 12 步。步骤只支持现有四个写工具，读取由编排器管理。`expectedRevision` 不进入计划，执行器在每次尝试前读取最新版本并注入。

规划输出先经过协议规范化：仅兼容将有效 `mode` 值写在 `type` 中的无歧义别名；两者同时存在时必须一致。随后仍完整校验计划、工具参数、引用与请求边界，保存的计划只使用 `mode`。被拒绝候选记录模型、尝试次数及顶层字段摘要，不保存原始输出正文。

创建步骤的输出可以通过 `{ "stepId": "前面的创建步骤ID", "index": 0 }` 引用，支持重命名、提示词、连接以及新节点的 `referenceNodeIds`。不接受前向引用、重复步骤 ID、未读取或不存在的节点 ID。

明确指定的新名称会按用户原文绑定；单一引用、单一输出的创建指令会绑定真实引用 ID，明确创建数量和类型会在计划阶段校验。

计划校验通过后，计划、上下文快照和全部步骤 ID 在事务中一次保存，然后才发出 `plan` SSE 事件并开始写画布。前端执行过程中显示计划，结束后移除执行过程展示。

## 状态与持久化

主路径：`planning → executing → verifying → completed`。

- `awaiting_input`：计划需要用户澄清，已回复问题并结束本轮；新消息重新规划，不执行猜测的操作。
- `partial`：已经提交部分操作，后续执行或最终核验失败。
- `failed`：本轮未提交写操作即失败。
- `interrupted`：执行流提前关闭、服务中断或超时，可从检查点显式恢复。
- `cancelled`：请求取消。已提交步骤保留，可显式恢复。

`CanvasAgentRun` 保存请求 ID、规范化输入哈希、原始输入、计划、上下文/预算统计、响应、错误分类、积分 hold 和交付时间。`CanvasAgentStep` 保存顺序、稳定步骤 ID、工具、参数、尝试次数、状态与提交结果。`CanvasChatMessage.runId` 与角色组成唯一键。

`completed` 表示执行和核验成功；`deliveredAt` 表示消息保存和对话积分结算已原子完成。二者分开，避免“操作已完成但回复交付中断”导致重复操作或重复扣费。

## 上下文与调用预算

- 每次规划最多 24,000 个保守估算输入 token；按 UTF-8 字节计文本，图片每张预留 2,048，最多保留当前请求的 4 张图。这是工程预算，不是模型厂商精确 tokenizer/图片 token 计费。
- 保留完整当前指令、优先收录明确引用与选中节点及直接依赖；其余节点提供索引，超预算的索引不进入模型。
- 相关节点提示词最多 1,500 字符、正文最多 4,000 字符，明确标记截断；关键资料不足时 Planner 应澄清，不把截断当全文。
- 数据库只加载最近 20 条历史消息；模型至多保留最近 3 轮，并按剩余预算裁剪。历史工具轨迹不重放为新任务。
- 最多 3 次规划候选尝试；共享预算约束实际 HTTP 请求最多 8 次、累计预留输出额度最多 65,536 token，包含厂商重试和协议兼容请求。
- 总执行期限 120 秒；主模型起始输出额度 4,096 token，截断时在预算内有限翻倍；备用思考模型至少 16,384，截断时在预算内升至 32,768 重试。
- Provider 在最终 HTTP 请求前再次估算输入，兼容协议重新包装也不能绕过预算。

## 幂等与并发

客户端为一次提交生成 `requestId`。唯一键为 `(conversationId, requestId)`；同一个 ID 携带不同输入会被拒绝。已完成请求返回保存的结果，不重新规划或执行，已交付请求不再次结算。

同一画布跨对话共用一个执行租约：45 秒到期，10 秒续租。接管过期租约时会标记旧任务中断。写步骤和任务状态更新都检查随机租约 token，并用画布行锁作为栅栏；旧执行器不能在租约被接管后继续提交。

画布修改和步骤 `completed/result` 在同一个数据库事务提交。工具返回丢失时，执行器先查询该步骤的持久化凭证；存在凭证便恢复结果，绝不盲目重复创建。

单步骤原子提交，整个多步骤任务不自动回滚。已经完成的操作在失败或取消后保留。人工编辑仍由 CAS 和字段前置条件保护；版本变了但目标未被修改可以重试，目标已被人工改变则停止，要求新指令。

## 错误恢复

- 模型 429：在当前规划请求输出前切换备用模型。
- 模型 429/5xx：在全局预算内有限重试；尚未执行画布操作。
- 无效 JSON/计划：最多 3 次修正，未校验通过前不写画布。
- 版本冲突/可识别的数据库事务冲突：重新读取后有限重试，单步至多 3 次尝试。
- 丢失执行响应：查询已提交凭证恢复。
- 目标改变、权限/业务错误、核验失败：停止；不自主改写已执行计划。需要新指令重新规划。
- 中断/超时：保留计划和已提交步骤，恢复时跳过已完成步骤，继续执行剩余部分，再核验。

## 接口

发送接口仍是：

`POST /canvases/:canvasId/conversations/:conversationId/messages`

新增可选 `requestId: UUID` 与 `resume: boolean`。恢复已有未交付任务时须沿用原始输入和请求 ID，并设置 `resume: true`。

也可直接恢复，服务端会读取原始输入，客户端无需重建：

`POST /canvases/:canvasId/conversations/:conversationId/runs/:runId/resume`

恢复接口返回同样的 SSE。会验证用户、画布和对话权限。已结束任务不会隐式恢复，普通新消息也不会重放旧任务。

对话详情中的 `agentRuns` 包含请求 ID、状态、计划、步骤状态/次数、错误分类；不返回租约 token。进程崩溃后过期租约在详情中呈现为中断，下一次领取时持久化该状态。

## 当前边界

这版是请求内执行、显式恢复的基础设施，没有后台队列持续执行、自动重规划或媒体生成能力。任意自然语言任务的语义覆盖仍依赖 Planner；程序核验已知字面约束和计划对应的实际状态，不能证明所有开放创作要求都已被理解。后续增加生成/剪辑工具时，应扩展计划 schema、事务/外部任务幂等和验证器，并为耗时任务接入后台 worker。
