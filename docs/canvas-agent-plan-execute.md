# 画布 Agent：Plan & Execute

## 执行边界

`ChatService → claim/积分预留 → ContextBuilder → Planner → 校验并保存计划 → Executor → Verifier → 消息与积分事务提交 → release`

Planner 只输出 JSON，不持有画布写工具，也不负责执行循环。Executor 使用已校验、已落库的计划执行 MCP 工具；它负责版本、步骤结果引用、重试与检查点。Verifier 比较计划预期与真实画布；最终操作回复由程序依据已核验结果生成。普通问答和澄清使用无执行步骤的计划。

当前请求独立决定操作权限。明确要求只回答、不修改画布，以及数量、状态、原因类只读问句，会限制规划协议为 `answer | clarify`，并在计划校验和执行入口拒绝写步骤；历史任务和引用正文不能授予本轮写权限。这是对明确只读表达的程序约束，仍不等于覆盖所有自然语言歧义。

当前使用显式的持久化状态机，替换原来模型自行决定下一次工具调用的 LangGraph 循环。数据库中的计划和操作凭证是恢复依据，不依赖进程内聊天消息或框架内存。

## 文件职责

- `canvas-agent.service.ts`：阶段编排、规划校验、执行、核验、取消、超时。
- `agent-plan.ts`：计划 Zod schema、从工具定义派生 Planner JSON schema、步骤依赖引用、用户明确名称与创建数量约束。
- `agent-context.ts`：上下文筛选、历史窗口、输入预算。
- `agent-store.ts`：请求幂等、画布租约、过期接管与写入栅栏、错误分类。
- `agent-verifier.ts`：并发编辑前置条件和执行结果验证。
- `canvas-tools.service.ts`：业务验证、权限、画布 CAS、画布修改与步骤凭证原子提交。

## 计划

```json
{
  "mode": "execute",
  "goal": "重命名目标节点",
  "answer": "",
  "steps": [
    {
      "id": "rename",
      "description": "将节点名称改为测试agent",
      "tool": "rename_node",
      "arguments": { "nodeId": "真实节点ID", "title": "测试agent" }
    }
  ]
}
```

`mode` 为 `execute | answer | clarify`。执行计划最多 12 步。步骤支持四个画布写工具及 `generate_image`，读取和状态查询由编排器管理。`expectedRevision` 不进入计划，执行器在每次尝试前读取最新版本并注入。

规划输出先经过协议规范化：仅兼容将有效 `mode` 值写在 `type` 中的无歧义别名；两者同时存在时必须一致。随后仍完整校验计划、工具参数、引用与请求边界，保存的计划只使用 `mode`。被拒绝候选记录模型、尝试次数及顶层字段摘要，不保存原始输出正文。

备用模型偶尔遗漏末尾数组闭合符或多输出闭合括号。解析器仅能根据已有结构修复末尾闭合括号，或移除完整对象之后多出的闭合引号与括号后缀；不补字段、值、逗号或字符串内容，不忽略后续正文或第二个 JSON 值；内部语法异常仍拒绝，修复后仍通过完整 JSON、计划、工具和权限校验。规划中断或达到输出额度限制仍走错误恢复，不能直接执行截断输出。

创建步骤的输出可以通过 `{ "stepId": "前面的创建步骤ID", "index": 0 }` 引用，支持重命名、提示词、连接以及新节点的 `referenceNodeIds`。不接受前向引用、重复步骤 ID、未读取或不存在的节点 ID。

对于“创建并填充正文，再重命名”，Planner 使用完整多步骤示例。若模型仍把节点 ID 写成“由 create_text 步骤生成的节点 ID”，仅在明确指向唯一的前序创建结果时转换为步骤引用对象；未知 ID、未知步骤、前向引用和含糊的多个候选仍拒绝，并给出可用引用对象供修正。

明确指定的新名称会按用户原文绑定；“基于/根据/引用某节点”创建时优先绑定明确来源，没有明确引用时使用当前选中节点，批量输出会逐个建立依赖。邻居上下文和引用素材正文中的 ID 不作为明确来源。普通独立创建不自动依赖选中节点，明确要求不连线时不会补引用。提示词内的节点引用也会转换为真实依赖连线，明确创建数量和类型会在计划阶段校验。

新节点位置由服务端统一安排在已有节点群的右边界之外，按媒体比例计算卡片宽度并留出160画布单位的间距，同一批次从上到下单列排布。同一任务拆成多次创建时，从已提交凭证恢复本轮纵列，继续向下排列；独立的新任务从更新后的右边界继续。提示词倍数生成的额外结果排列在原节点下方，同样使用共享的尺寸和避让规则，跳过已有节点；恢复或刷新不重排已有结果。图片依赖图片时使用与手动添加下游节点一致的兼容模型。画布收到新的依赖连接时自动显示连线。

更新提示词保留已有有效依赖，并补齐引用标记和连线。对已存在连线再次连接时也会修复缺失的引用元数据；核验同时检查真实连线和目标节点引用列表。

计划校验通过后，计划、上下文快照和全部步骤 ID 在事务中一次保存，然后才发出 `plan` SSE 事件并开始写画布。前端执行过程中显示计划，结束后移除执行过程展示。

## 状态与持久化

画布操作路径：`planning → executing → verifying → completed`。图片生成路径在提交核验后进入 `waiting_generation`，经后台核验后进入 `completed | completed_with_errors`。

- `waiting_generation`：已保存的图片计划正在等待名额或生成结果；可以交付当前进度，但不属于执行终态。
- `completed_with_errors`：生成任务均已结束，其中有失败项。成功项保留，失败项可单独重试。
- `awaiting_input`：计划需要用户澄清，已回复问题并结束本轮；新消息重新规划，不执行猜测的操作。
- `partial`：已经提交部分操作，后续执行或最终核验失败。
- `failed`：本轮未提交写操作即失败。
- `interrupted`：执行流提前关闭、服务中断或超时，可从检查点显式恢复。
- `cancelled`：请求取消。已提交步骤保留，可显式恢复。

`CanvasAgentRun` 保存请求 ID、规范化输入哈希、原始输入、计划、上下文/预算统计、响应、错误分类、积分 hold 和交付时间。`CanvasAgentStep` 保存顺序、稳定步骤 ID、工具、参数、尝试次数、状态与提交结果。`CanvasChatMessage.runId` 与角色组成唯一键。

`completed` 表示执行和核验成功；`deliveredAt` 表示消息保存和对话积分结算已原子完成。二者分开，避免“操作已完成但回复交付中断”导致重复操作或重复扣费。图片计划在发出 `plan` 事件前保存用户消息和执行中回复，并结算一次规划对话积分；生成积分由各生成任务独立预留、成功扣除或失败退款。后续后台续跑不调用规划模型，也不再次收取对话积分。

## 上下文与调用预算

- 每次规划最多 24,000 个保守估算输入 token；按 UTF-8 字节计文本，图片每张预留 2,048，最多保留当前请求的 4 张图。这是工程预算，不是模型厂商精确 tokenizer/图片 token 计费。
- 保留完整当前指令、优先收录明确引用与选中节点及直接依赖；其余节点提供索引，超预算的索引不进入模型。
- 图片可见性依据实际附带的图片数量生成，规划阶段重建系统消息时仍保留；视频未提取帧时不能声称看到画面。聊天图片 URL 必须属于当前用户，拒绝跨用户、路径穿越及越出用户目录的符号链接。
- 相关节点提示词最多 1,500 字符、正文最多 4,000 字符，明确标记截断；关键资料不足时 Planner 应澄清，不把截断当全文。
- 数据库只加载最近 20 条历史消息；模型至多保留最近 3 轮，并按剩余预算裁剪。历史工具轨迹不重放为新任务。
- 最多 3 次规划候选尝试；共享预算约束实际 HTTP 请求最多 8 次、累计预留输出额度最多 65,536 token，包含厂商重试和协议兼容请求。
- 每次规划/执行连接的期限 120 秒；媒体任务通过持久化队列独立执行，等待结果不占用该连接或租约；主模型起始输出额度 4,096 token，截断时在预算内有限翻倍；备用思考模型至少 16,384，截断时在预算内升至 32,768 重试。
- Provider 在最终 HTTP 请求前再次估算输入，兼容协议重新包装也不能绕过预算。

## 幂等与并发

客户端为一次提交生成 `requestId`。唯一键为 `(conversationId, requestId)`；同一个 ID 携带不同输入会被拒绝。已完成请求返回保存的结果，不重新规划或执行，已交付请求不再次结算。

同一画布跨对话共用一个执行租约：45 秒到期，10 秒续租。接管过期租约时会标记旧任务中断。写步骤和任务状态更新都检查随机租约 token，并用画布行锁作为栅栏；旧执行器不能在租约被接管后继续提交。

画布修改和步骤 `completed/result` 在同一个数据库事务提交。工具返回丢失时，执行器先查询该步骤的持久化凭证；存在凭证便恢复结果，绝不盲目重复创建。

单步骤原子提交，整个多步骤任务不自动回滚。已经完成的操作在失败或取消后保留。人工编辑仍由 CAS 和字段前置条件保护；版本变了但目标未被修改可以重试，目标已被人工改变则停止，要求新指令。

## 错误恢复

- 模型 429：在当前规划请求输出前切换备用模型。
- 模型 429/5xx：在全局预算内有限重试；尚未执行画布操作。
- 无效 JSON/计划：最多 3 次修正，未校验通过前不写画布。
- 版本冲突/可识别的数据库事务冲突：重新读取后有限重试，单步至多 3 次尝试。
- 临时数据库断连/连接池超时保留可恢复分类；读取上下文遇到临时错误最多尝试 3 次。模型网络错误归入模型不可用，在规划预算内重试。
- 丢失执行响应：查询已提交凭证恢复。
- 目标改变、权限/业务错误、核验失败：停止；不自主改写已执行计划。需要新指令重新规划。
- 中断/超时：保留计划和已提交步骤，恢复时跳过已完成步骤，继续执行剩余部分，再核验。

## 接口

发送接口仍是：

`POST /canvases/:canvasId/conversations/:conversationId/messages`

新增可选 `requestId: UUID` 与 `resume: boolean`。恢复已有未交付任务时须沿用原始输入和请求 ID，并设置 `resume: true`。

也可直接恢复，服务端会读取原始输入，客户端无需重建：

`POST /canvases/:canvasId/conversations/:conversationId/runs/:runId/resume`

恢复接口返回同样的 SSE。会验证用户、画布和对话权限。普通画布操作的已结束任务不会隐式恢复，普通新消息也不会重放旧任务。已交付的图片计划在连接断开或服务重启后由后台续跑原计划；业务错误、目标改变或核验失败不会自动改写计划。

对话详情中的 `agentRuns` 包含请求 ID、状态、计划、步骤状态/次数、错误分类；不返回租约 token。进程崩溃后过期租约在详情中呈现为中断，下一次领取时持久化该状态。

## 当前边界

第二阶段已接入异步图片生成与后台续跑。暂未接入视频生成、音频生成或智能剪辑工具，也不做自动重规划。图片生成步骤必须放在所有画布编辑步骤之后，暂不支持依赖本轮尚未完成图片的后续生成/编辑操作。每个 `generate_image` 生成一张图片，多张分别创建节点和步骤，仍受整份计划最多12步的约束。

任意自然语言任务的语义覆盖仍依赖 Planner；程序核验已知字面约束、任务与节点绑定、素材归属和实际状态，不能证明所有开放创作要求都已被理解。画布保存使用可选 `baseGraph` 合并本地修改与后台结果，尚不属于完整多端协同编辑系统；不传基线的旧客户端仍使用整体图覆盖语义。

## 第二阶段：异步图片生成

- MCP `generate_image({nodeId, expectedRevision})`：使用图片节点的提示词、模型、尺寸和真实依赖提交生成。必须有执行器注入的持久化 `runId/stepId/lease token`；外部请求不能伪造这些内部作用域。生成工具只提交任务，不声称图片已完成。
- MCP `get_image_generation_status({taskId})`：校验用户与画布归属后查询任务，不重新提交、不扣费。状态查询不进入 Planner 的执行步骤。
- `canvas-image-tools.service.ts`：将稳定步骤 UUID 用作生成 `requestId`；生成任务、素材占位、生成积分预留、画布生成状态和步骤提交凭证在同一事务内保存。事务中不调用模型提供商，由既有生成队列在提交后派发。
- `canvas-generation-recovery.service.ts`：每3秒分页扫描持久化任务；通过 MCP 查询结果，核验素材归属与可用性，再更新画布和原助手消息。多个 PM2 实例通过同一画布租约、行锁和回执防止重复执行。
- 回写在画布行锁内重新读取持久化任务，防止另一个实例持有的旧 MCP 快照回退已完成结果。排队期间人工修改尺寸、质量、目标素材或任务绑定会停止旧计划，要求新指令。
- 生成名额不足时，步骤保留为 `pending`，Run 进入 `waiting_generation`。名额释放后执行器继续原计划，跳过已提交步骤。断线、过期租约和可恢复执行中断也沿用原计划；不重新调用 Planner。
- 提交首个媒体任务之前，先完成画布编辑阶段核验并持久化 `editsVerified` 检查点；续跑不再用旧标题核验该阶段，已提交节点的重命名或删除不会妨碍其他图片任务。提示词、依赖、尺寸等实际生成输入仍受前置条件保护。
- 已提交媒体任务由既有生成 worker 处理，页面关闭或 API 重启不重复提交。厂商返回不确定结果时保留 `unknown`，提示用户继续查询，不能自动重新发起付费生成。
- 结果写回只更新仍绑定原任务的节点；保留节点名称、提示词和位置，不重建已删除节点，不覆盖后续新任务。生成结果始终保留在生成历史。
- 对话通过 `backgroundPending` 轮询可续跑的图片计划，覆盖执行中、等待生成和可恢复中断；同步后台新增节点与引用列表，并刷新既有画布生成任务查询。前端只观察结果，不再次提交生成。
- `mergeCanvasGraphs` 使用观察基线保留用户对标题、提示词和位置的修改、显式删除，以及并发新增节点/连线和最新生成状态；自动保存与后台同步共用串行队列。保存携带基线，API JSON 请求上限为16 MB，避免大型画布触发默认100 KB限制。
- 同一客户端的排队保存使用前序写入的意图基线，保留慢网络下的删除/撤销和新增/删除顺序；同步读取失败不会阻断下一次 Agent 提交。
- 任务状态转换推进既有任务项 `revision`，DTO 状态版本为各任务项版本之和。节点和回执记录 `generationRevision`，浏览器拒绝旧任务快照。对话仅公开生成任务 ID/版本，不向客户端展开步骤提交正文。
- 手动恢复原生成任务时，后台会重新观察旧运行记录并更新原回复，覆盖任务先完成、扫描后发生的时序；浏览器在原回执版本追上当前任务之前持续刷新。部分计划因参数变化已停止时，只更新已提交任务的结果，不自动恢复被拒绝的后续步骤。
- 需要实际图片生成意图，单纯创建节点、生成提示词或明确禁止出图不能触发生成工具。这是已知表达约束，含糊指令仍应澄清。

验收语句：`根据故事节点拆成三个分镜，创建三个图片节点，分别填写提示词并生成图片。`
